# Design the Run

Read `AGENTS.md`, the root `README.md`, shared config and principles, and every selected package manifest and lint state before launch.

- Treat one package as one experimental unit. Choose deliberately different genres, research burdens, voices, structures, and audiences.
- Fix the common harness before authorship: skills, universal principles and obligations, graph factory, layer order, stage semantics, compiler gates, output language, review completion, and any scale target. Read `config/docs/obligations/common.md`, verify that the factory applies it as a no-exclusion checklist to every authored unit, and make every owner read the applicable `$novel` phase contract.
- Complete and merge the run's planned shared harness changes before authorship. Start package writing from a fresh branch and draft PR so a benchmark cannot hide or depend on unreviewed shared exceptions.
- Before launch, inventory each package's explicit user directives, seed, assets, existing canon, relevant history, and known work-specific constraints. Preserve direct directives without semantic compression, identify their authority, and place every already-adopted rule through `$novel` [Work-Specific Contract](../novel/work-specific.md). Leave further discovery to the owner's opening contract pass; do not pretend an unexamined package has no special rule.
- For an existing or rebuilt work, inspect relevant Git history before calling the package empty or choosing a new scale. Record the earlier files, H2/H3/H4 counts, authored body size, research breadth, and promised delivery scope as regression evidence. An evidence-schema migration changes declarations and reviews; it does not authorize deleting or shrinking authored content. Discard or reduce it only under an explicit user-approved scope change.
- Design each package's initial extra graph independently. Keep the explicit `claims` array empty only when the work-specific audit finds no independent target; otherwise append typed claims only in that package's `lint.config.ts`. Classify each target through `$novel` and `$evidence-graph`, then declare its family, authority, host and reference populations, cardinality, exclusion behavior, stage, and review rule in the benchmark brief. A benchmark may test genre conventions, research duties, formal constraints, or additional cross-layer relationships without pretending they bind every novel.
- Do not promote a successful package rule into `config/docs/principles` during the run. Record it in `.wiki`, compare counterexamples across works, and promote it only when it survives the shared instruction contract's universality test.
- Announce the lineup in the benchmark issue or draft PR and keep resumable status under `.wiki/benchmarks`. The root README may retain stable package catalog metadata required by `AGENTS.md`, but never benchmark progress, owner activity, or readiness status.
- Create new units only with `pnpm create:novel`. Complete the installation and repository gates required by `AGENTS.md` before agents start. Scaffolding creates structure, not story content.
- Define observations beforehand: elapsed transitions, diagnostics repaired, upstream revisions, stale reviews renewed, literary findings, clean review rounds, and per-layer scope/depth regression measures. Counts are alarms rather than merit scores, but an unexplained simultaneous collapse in files, units, body size, or research breadth blocks the common proportional-development obligation. Without a designed control, call the result exploratory rather than causal proof.
